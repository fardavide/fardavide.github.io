# Decisions

Key choices and why (ADR-style, newest last). Several were settled with the user during design.
Check here before re-litigating.

## Vite + vanilla TypeScript, no framework

The design is hand-authored HTML and CSS with scroll-driven animations; nothing in it needs a
component model. Vite gives a dev server, a hashed production build and TypeScript in strict mode
for the few lines of logic. Astro lost because its multi-page and content features buy nothing for
a single page. Plain HTML with no build lost because it leaves no place for a type check, a lint
or a unit test to run. Chosen with the user on 2026-09-19.

## Public repository named `fardavide.github.io`

A GitHub user site is served from the root of `fardavide.github.io`, so Vite's `base` is `/` and
never changes when the custom domain is attached. A project site (`website`, `fardavide.dev`)
would have lived under a path until the domain was attached and needed a base-path change at that
moment. Public because GitHub Pages does not publish private repositories on the Free plan and
because rulesets only apply to public repositories there. Chosen with the user on 2026-09-19.

## npm, not pnpm

pnpm is not installed on the development machine and installing tools globally is machine
configuration the agent does not touch. npm ships with Node 24 and its lockfile is committed.

## MIT for the code, content reserved

The user chose MIT over no licence (what Aura and Granita carry). The README says the text, the
name and the app screenshots are not part of the grant.

## Screenshot tests: Playwright, recorded on a Mac, verified on `macos-26`

The kickstart default for web is Playwright in its Linux Docker image at both ends. Docker is not
installed here and installing it is machine configuration. A Linux runner verifying Mac-recorded
baselines lost because oltre measured a 5 to 7.5 percent pixel drift between the two renders on
nearly every frame, which forces a blanket tolerance that hides real regressions. So the
comparison stays byte-exact by running the CI job on a macOS runner, as oltre does, pinned to
`macos-26` to match the recording machine. Baselines are never regenerated by CI.

## Publishing mirrors oltre.space

The user asked that publishing follow the Oltre project: a `pages.yml` workflow builds the site
and pushes it to a `gh-pages` branch, and GitHub Pages serves that branch with a CNAME and HTTPS
enforced. `actions/deploy-pages` with an artifact lost to that directive. Not implemented at the
time of writing; see `status.md`.

## Presentation only, no domain or data layer

The site has no data, so there is nothing for a domain or data layer to hold. Per the kickstart
stack reference, a UI-only feature starts as just presentation. The one piece of logic, the theme
override, is kept in a pure module so it can be unit-tested; the DOM wiring is covered by
screenshot tests. A second layer is added when something needs it, not in anticipation.

## Agent config under `.ai/` with native adapters

Shared agent content (guide, skills, docs) lives in `.ai/`, and `AGENTS.md`, `CLAUDE.md`,
`GEMINI.md` and the per-tool `skills` directories are symlinks into it. This matches oltre and the
user's global harness, so any of Claude Code, Codex or Gemini opens the repo with the same
instructions. A `.claude/`-only layout lost because it would need duplicating the moment a second
tool is used. Host-specific settings stay in `.claude/`.
